## Computer Science Portfolio - Reflections & Agile Process

### Interpreting User Needs and Implementing Programs
Interpreting user needs involves closely analyzing client requirements and breaking them down into manageable, actionable components. By translating business problems into structured software specifications, we ensure that the resulting code directly serves the user's intended goals.

### Creating User Stories
Creating user stories helps bridge the gap between high-level project goals and technical execution. By focusing on *who* needs a feature, *what* it is, and *why* it matters, user stories keep the development team aligned on delivering continuous value through the software development lifecycle (SDLC).

### Incorporating Agile Processes
Incorporating Agile processes—such as iterative sprints, daily stand-ups, and retrospectives—allows teams to adapt quickly to changes, manage risks, and maintain continuous communication. This flexible approach fosters strong team collaboration and ensures high-quality product delivery.

This section details the system analysis, requirements gathering, and architectural design processes completed for the **DriverPass** project.

* **Project One Artifact:** Business Requirements Document (`Business_Requirements_Document.docx`)
* **Project Two Artifact:** System Design Document (`System_Design_Document.docx`)

### CS 255 Module Eight Reflection

#### 1. Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?
The client for this project was **DriverPass**, a company focused on helping student drivers successfully prepare for and pass their driving tests. They wanted a comprehensive, web-based, cloud-hosted application designed to streamline student onboarding, provide access to online practice exams and study resources, and manage scheduling for on-the-road driving lessons. The system required distinct user roles—including customers (students), instructors, and administrative staff/owners—each with tailored permissions to schedule, modify, or cancel appointments, track lesson notes, and manage user data securely.

#### 2. What did you do particularly well?
I excelled at translating qualitative stakeholder interview transcripts into structured, granular functional and non-functional requirements. By clearly separating performance metrics, platform constraints, and security requirements in the Business Requirements Document, I established a solid foundation for the subsequent design phase. Additionally, creating the UML diagrams (use case, activity, sequence, and class diagrams) using Lucidchart allowed me to effectively map out both object-oriented relationships and complex process flows, bridging the gap between high-level user expectations and technical system architecture.

#### 3. If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
If I could revise one aspect of my work, I would refine the complexity and notation clarity of the UML activity and sequence diagrams. While the logic accurately captured the system workflows, some of the decision branches could have been simplified to improve readability for non-technical stakeholders. In the future, I would break down intricate multi-actor processes into modular sub-diagrams to ensure that both technical developers and business clients can parse the system logic instantly.

#### 4. How did you interpret the user’s needs and implement them into your system design? Why is it so important to consider the user’s needs when designing?
I interpreted the user's needs by systematically breaking down the client interview transcripts into core operational components, user roles, and system constraints. Each stated objective—such as secure credential validation, automated appointment scheduling, and role-based access control—was translated directly into functional requirements and modeled visually through UML diagrams. Considering user needs early and continuously throughout the design process is vital because it aligns stakeholder expectations, prevents costly scope creep, and ensures the final software delivers genuine practical value to both end-users and administrators.

#### 5. How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?
My approach to software design follows a structured, top-down lifecycle methodology. I start with thorough requirements gathering to define *what* the system must achieve before determining *how* it will be built. Moving forward, I plan to rely heavily on structured modeling techniques—combining process modeling (to map out workflows and business logic) with object modeling (to define system classes, attributes, and relationships). Utilizing Computer-Aided Software Engineering (CASE) tools like Lucidchart alongside rigorous documentation ensures that every phase of system development remains traceable, scalable, and aligned with client goals.
